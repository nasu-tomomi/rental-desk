# Rental Desk 要件定義

## 概要

スキー・スノーボードレンタル店の予約・受付・貸出・返却を、紙の管理からデジタル化する受付管理アプリ。
1番の目的は、朝の受付が混み合う時間帯に、お客様の待ち時間を短縮し、スムーズにレンタル引渡しスタッフに流せるようにすること。

## 現行業務と課題

現行の業務フローは次のとおり。

- ネット予約は予約メールを印刷して紙で管理する
- 当日来店のお客様は、紙の申込書に手書きで記入する
- 貸出時は紙の控えを渡し、返却時は控えと照合する
- 繁忙期は1日に100組近い予約がある

課題：

- 「誰が来店済みで、誰がまだ返却していないか」が一目で分からない
- 紙の申込書には料金が印刷されておらず、スタッフが料金を暗記し、電卓で計算して会計している
- お客様の約9割が海外の方で、連絡手段は電話だけでは不十分（LINE／WhatsAppが必要）

追加の課題：

1. 重複予約への備え

- 同じ内容の予約が2件入った場合、「誤った二重登録」か「正しい2件目」かをシステムでは判定できないため、自動で弾いたり消したりはしない
- スタッフが予約一覧で「要確認」の印を付けられる機能を今後の課題とする（印の予約は来店前に電話などで確認する）
- きっかけ：2026-10-31の動作確認で、登録操作の再実行により同一予約が2件登録されることを実際に確認した

2. 家族内で別々に返却するケースへの対応

- 現状、返却予定日は予約単位で1つとしている。家族全員が同じ日に返却するのが基本だが、家族の中で別々に返却に来る場合もあり得るため、利用者ごとに返却状況を管理できる仕組み（個人別の返却済みの印など）は今後の課題とする。

3. 小物欄の入力方式（候補チップと自由入力の併用）

- 小物は、事前に予約するお客様もいれば、当日追加するお客様もいる。プルダウン一択にすると、ネット予約から届く自由文のデータを受け取れず、欠けてしまう
- そのため、よくある小物の候補チップ（複数選択可）と自由入力欄を併用し、保存形式は今と同じ1つの文字列とする方針を決定した（2026-11-02）
- 優先順位は「データが落ちないこと ＞ 入力の楽さ」とする。実装は今後の課題

4. 品目プルダウンの判別しやすさ

- 品目名が長く、プルダウンを閉じた状態では「セット」か「フルセット」か判別できない
- 先頭にのような種別タグを付ける表示を検討する

5. QRコードで進めるステータスと、お客様側の画面

- 引渡しはフロントを離れた場所で行うため、その場でアプリに入力する余裕がない
- 来店時の「チェックイン」、出発時の「出発済み」、返却確認後の「チェックアウト」を、お客様またはスタッフのQR読み取りで進める方式を検討する
- お客様自身が自分の予約データを見られる画面も、あわせて検討する

6. 予約番号の種別分け（検討中）

- 現在、事前予約と当日受付は同じ予約番号の系列で管理している
- 一覧での判別は、予約時間の有無（事前予約にはあり、当日受付にはなし）、または source（net / walk-in）で行える
- 検討案：①番号は1系列のままにし、source をバッジ表示して区別する ②予約番号自体を種別で分ける
- 現場で口頭確認する際の分かりやすさを踏まえて、引き続き検討する

## 目指す受付フロー（来店〜貸出）

1. スタッフが「本日の予約一覧」を開く（その日の予約が全部見える）
2. お客様の名前・フリガナで検索し、すぐ予約が見つかる
3. 予約内容（レンタル品・人数など）を確認する
4. ボタン1つでステータスを「貸出中」に変更する
5. 返却時はボタン1つで「返却済」に変更する

## 機能要件（MVP）

- 予約の登録・一覧表示・削除
- 本日の予約一覧の表示
- 名前・フリガナでの検索（ローマ字にも対応）
- ステータス管理（予約済 → 受付済 → 貸出中 → 返却済、予約単位。予約済・受付済からはキャンセルへも変更できる）
- 料金の自動計算（料金マスタを参照）
- 利用者ごとにメイン品目に加えて複数の追加品目を登録し、追加品目の料金も自動計算する
- 当日来店のお客様の簡易登録（名前・電話・品目・人数・貸出日・返却日）

## 将来拡張（MVPには含めない）

- 支払い状況の管理
- CSV取込（ネット予約の一括取り込み）
- QRコードによる備品管理
- WordPress予約システムとの連携

## 料金計算のルール

- 料金は「品目 × 区分（おとな／こども）× 日数」で決まる
- 日数の料金パターンは3つだけ：1日料金／2日料金／3日目以降は1日ごとの加算
  - 計算式：1日＝1日料金、2日＝2日料金、3日以上＝2日料金＋（日数−2）×3日目以降料金
- カテゴリはスタンダード、BURTON 2027、ハイグレードの3種
- こども料金は小学生以下が対象。返却時間は17:00
- 料金データは料金マスタ（docs/03-prices.csv）に持つ

## 追加品目の仕様

- 利用者はメイン品目を1つ持ち、必要に応じて追加品目を0〜複数件登録できる
- 追加品目は料金マスタから選択し、reservation_user_items に保存する。各レコードは id（PK）、reservation_user_id（FK → reservation_users.id）、price_master_id（FK → price_master.id）を持つ
- メイン品目・追加品目とも、利用者の区分（おとな／こども）と日数で料金を計算する。品目ごとの独立した日数は持たない
- 利用者の金額＝メイン品目の料金＋追加品目の料金の合計。追加品目がない場合はメイン品目の料金のみとする
- 予約の合計金額は、追加品目を含む各利用者の金額の合計とする
- 小物欄（small_items）の候補チップ・自由入力をまとめた文字列は保持する。料金計算の対象となる追加品目は reservation_user_items で管理し、小物欄の文字列から自動で料金を計算しない

## 設計の前提（元の業務資料から）

- 予約1件＝「申込者1人＋利用者1〜複数人（最大20人ほど）」。利用者ごとにレンタル内容とサイズが違うため、予約と利用者は別のテーブルに分ける（詳細は設計メモ docs/02-er-diagram.md）
- 受付一覧で必要なのは、受取店舗・レンタル日時・申込者名（フリガナ）・電話・利用者数・レンタル内容・スキー場・支払い方法・ステータス。住所やメールは一覧に出さない
- 紙の申込書にある「返却日時」と「実際に貸したサイズのメモ」は、アプリにも項目として持つ

## 技術構成

- バックエンド：Java / Spring Boot（REST API）
- フロントエンド：React
- データベース：MySQL（Dockerで起動）
- リポジトリ構成：1つのリポジトリに backend / frontend フォルダを分ける
